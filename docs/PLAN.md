# K1Remote 实现计划

远程对讲机工作站：把 **UV-K5 V1**（自研固件 `uv-k5-firmware-custom-remote`，V1 固件 + 串口控制）放到信号好的高处，通过树莓派 + 互联网在浏览器里完成 **远程收听、远程发射（PTT）、远程控制（看屏幕/按键/换信道）**。
第一阶段只做局域网（后续用 WireGuard 打通两端网络），公网直连列为后期演进。

## 0. 结论先行

1. **语音传输用 WebRTC：可行，且是浏览器场景下的最优解**（评估见 §3）。Pi 端用 Python `aiortc`，语音编解码用 Opus（16kHz 单声道，~24kbps），预留 PCMU 降级路径。
2. **屏幕/按键远程控制直接复用固件内置的 K5Viewer 串口协议**：屏幕差分流与按键注入帧在 v1/v3 两固件间完全一致，服务端协议库一套代码双固件通用（差异仅波特率与保活扩展位，已做成变体配置）。
3. **远程 PTT（定稿，零固件改动）**：**DTR/RTS 电平 PTT（→ PTT1，3.5mm Sleeve 触点）+ 发射期暂停保活**。
   - 实测：UV-K1 的 K 型口**有**外部 PTT 感测（早期"无外部 PTT 电路"的结论有误，已撤销）；DTR=1 & RTS=0 可键动对讲机。
   - 关键机制（AIOC 固件 `usb_serial.c`/`settings.h` 源码确认）：PTT1 与主机→对讲机串口数据（PA9）共用 Sleeve 触点；`TXFRCPTT` 默认= PTT1，**每次串口数据发送前 AIOC 会强制释放 PTT1**（数据优先），数据停发且 UART 空闲后才重新吸合。因此 PTT 吸合期间必须静默保活/注入——静默只停 bulk 数据，DTR/RTS 控制传输不受影响，看门狗随时可撤 PTT。
   - 发射期间屏幕流暂停属预期（保活停止 + `RXIGNPTT` 默认丢收流），松键后恢复并补整帧。
   - 曾评估 CM108 HID GPIO4→PTT2（Tip 触点，与串口物理分离、不受 TXFRCPTT 影响）作为免静默方案，因 PTT 引脚与机型键控位置对不上而弃用（用户实测决策）。
   - 串口帧 PTT（`AA 55 06`，固件补丁）仅存档于固件源码作备份，不参与本方案、无需刷机。
4. **音频必须走模拟通路**：收/发 音频经声卡进出对讲机喇叭/麦克风接口。V1 的 K 型口线上 **UART 数据与音频物理混线**（tip = 喇叭音频 + UART TX；ring = 麦克音频 + UART RX + PTT），音频质量与纯净度是 V1 方案的主要工程点（见 §4.2）。
5. 技术栈：**Python 3 + pyserial + sounddevice + aiortc + aiohttp**（服务端），**原生 ES Modules + Canvas**（前端），单机单服务，systemd 托管。

## 1. 固件侧调研结论（依据 `uv-k5-firmware-custom-remote` 源码）

### 1.1 物理连接

- 对讲机 K 型两芯口 ← **Baofeng/Kenwood 式编程线**（CP2102/CH340 USB-UART 桥）→ 树莓派 USB 口，枚举为 `/dev/ttyUSB0`，**波特率 38400**（固件 `UART1->BAUD = 48M/39053`）。
- 协议细节见 `docs/protocol-k5viewer.md`（v1 为主体、v3 差异为附录），速览：

| 方向 | 帧 | 说明 |
|---|---|---|
| 主机→机 | `55 AA 00 00` | 保活（100ms 周期；v1 **只有**纯保活，v3 的扩展保活 `55 AA 05 xx` 在 v1 上不算保活） |
| 主机→机 | `AA 55 03/04 <key>` | 注入短/长按键（keycode 两固件一致） |
| 机→主机 | `0xF0\|flags` + `AA 55 02 len + 块×N + 0A` | 屏幕差分流；flags 低 3 位 = 深睡/红灯(TX)/绿灯(RX) |

- 屏幕差分：128×64 单色，128 个 8 字节位平面块，仅传变化块，整帧 ~1.3KB；38400 波特下整帧约 240ms（推流为阻塞发送，属于已知特性，见 §8 风险）。
- **无 RF Log 功能**（v3 专属扩展，v1 固件不发送 0x05/0x06 帧）→ Web 状态面板的电池电压等数据在 v1 上不可用，改由 UI 自行汇总（RX/TX/频率从屏幕流与按键操作推断，后期可用 legacy 协议读 EEPROM 补齐）。
- 固件在物理按键按住期间跳过推流；CHIRP 占串口时锁定推流（`gUART_LockK5Viewer`），均属正常。
- 固件另有旧版整帧截图功能（`screenshot.c`，无 0xF0 标记的 `AA 55 01` 帧）——客户端解析器按"无标记即丢弃"自动忽略。

### 1.2 远程 PTT 的实现依据（定稿）

- **K 型口触点-方向表**（依据 AIOC 原理图 `kicad/k1-aioc` 设计注释，K1 双 TRS 插头）：

  | 触点 | 信号 | 方向 |
  |---|---|---|
  | 2.5mm Tip | SPK+ 喇叭音频（→ AIOC 采集） | 对讲机 → 主机 |
  | 2.5mm Ring | 对讲机 TXD（屏幕流数据，→ PA10） | 对讲机 → 主机 |
  | 2.5mm Sleeve | GND | — |
  | 3.5mm Tip | +V / PTT2 | 主机 → 对讲机 |
  | 3.5mm Ring | MIC+ 麦克风音频（← DAC） | 主机 → 对讲机 |
  | 3.5mm Sleeve | **对讲机 RXD（保活/注入）+ PTT1**（split-pad 默认连通） | 主机 → 对讲机 |

- **保活**：主机每 ~100ms 发 `55 AA 00 00`，固件每收到合法协议帧刷新 keepAlive 计数（15 个主循环周期），归零停止推流；恢复保活即补整帧。
- **PTT 仲裁机制**（源码级，`usb_serial.c` 两处独立机制，都必须满足）：
  1. **TXFRCPTT 强制释放**（默认=PTT1）：每次 CDC 数据发送前强制释放 PTT1（数据优先）→ PTT 吸合期间必须静默数据，否则 PTT 被反复释放、对讲机 30ms 防抖永不满足（实测复现）；
  2. **TE 忙丢弃**：DTR/RTS 线状态回调到达时若 UART 发送器忙（TE=1），**该次 PTT 变更直接丢弃**（不排队不重试）→ 键上瞬间必须无在途数据，且断言尽量合并到单次线状态变更；释放撞上 TE 忙同样会被丢（卡发射风险），释放后需补一次线状态翻转重申。
- **定稿方案**：静默先行（≥0.25s 无数据）→ 单回调断言（先 setRTS(False) 后 setDTR(True)）→ 保持（静默）→ 释放 + 重申兜底；探测工具 `--ptt-test` 已内置完整状态机（含盲重试一次，防御残余竞态）。
- **定稿方案**：DTR=1 & RTS=0 键上（控制传输，静默期间看门狗仍可随时撤 PTT）+ 吸合期暂停保活/注入 + 释放后恢复。
- 屏幕流红灯位是权威 TX 状态回读 → 客户端"目标状态 + 差异重试"。注意：PTT1 吸合期间收流被 `RXIGNPTT` 丢弃，红灯位只在键上前/释放后可读，发射期间的 TX 确认依赖对讲机自身指示（部署时配 TxTOut 兜底）。
- 串口帧 PTT（`AA 55 06 <0|1>`，固件补丁已实现并存档）作为"纯编程线无 AIOC"部署的备份能力。

### 1.3 Legacy CPS 协议（`app/uart.c`）

V1 原版 CPS 协议（0x0514 版本查询、EEPROM 读 0x051B / 写 0x0529 等）保留完整。**读**可用于导出信道表、电池/型号信息展示；**写**风险高，第一阶段不开放写 EEPROM。这也是 v1 上补齐状态面板数据的主要途径（M5 可选项）。

## 2. 系统架构

```
┌─────────────── 浏览器（操作端）───────────────┐
│  Canvas 屏幕镜像   虚拟键盘/信道控制            │
│  PTT 大按钮        音量/状态面板               │
│  听: WebRTC 接收   说: getUserMedia→WebRTC发送 │
└───────┬───────────────────┬────────────────┘
        │ WebSocket(控制/信令/屏幕帧, TLS)    │ WebRTC SRTP(双向语音)
        ▼                                   ▼
┌─────────────────────── 树莓派（k1remote 服务端）───────────────────────┐
│  webapp    : HTTPS 静态页 + WebSocket（登录鉴权、屏幕帧下发、指令上行）   │
│  webrtc    : aiortc Peer —— 发"对讲机收音"轨，收"操作员麦克风"轨          │
│  ptt       : PTT 状态机（目标态/回读/看门狗/发射期串口静默）              │
│  radio     : K5Viewer 串口协议（保活、差分屏解码、按键注入）              │
│  audio     : ALSA 采集 / 播放（声卡 ↔ 对讲机音频通路）                   │
└──────┬───────────────────────────────────────────────┬───────────────┘
        │ USB-UART 编程线（K型口, 38400）                  │ USB 声卡（音频通路见 §4.2）
        ▼                                               ▼
┌──────────── UV-K5 V1 (uv-k5-firmware-custom-remote) ────────────┐
│   K5Viewer 推流 / 按键注入 / OnePush PTT    喇叭 ──┬── 麦克风      │
│                                        (K型口线上与UART混线)     │
└────────────────────────────────────────────────────────────────┘
```

### 数据流要点

- **屏幕**：Pi 解码差分帧 → 合成 128×64 位图 → WebSocket 二进制下发（仅变化帧）。浏览器 Canvas 放大渲染（琥珀色磷光风格已实现）。
- **控制**：WS JSON 指令 `key`（键码+短/长按）、`ping`；服务端统一仲裁（单操作员锁）。
- **PTT 状态机**：UI 维持期望态，服务端以屏幕流红灯位为权威；不一致则重发注入指令；看门狗包括：WS 断连即撤 PTT、最长连续发射时限（默认 180s，可配）、服务崩溃由 systemd 拉起且恢复后强制撤 PTT、对讲机侧 TxTOut 超时兜底、**发射期间串口静默（音频优先）**。
- **音频（听）**：声卡采集 → aiortc Opus 编码 → SRTP → 浏览器原生播放。
- **音频（说）**：浏览器 getUserMedia → WebRTC → Pi 解码 → 仅在 PTT 有效时写入声卡播放到对讲机麦克风通路；PTT 未激活时静音丢弃。

## 3. 语音方案评估

### 3.1 候选对比

| 方案 | 单向时延 | Pi 端复杂度 | 浏览器端 | 公网演进 | 结论 |
|---|---|---|---|---|---|
| **A. WebRTC（aiortc / 浏览器）** | ~80-150ms | 中（现成库） | **原生播放+jitter buffer+回声消除** | 加 TURN 即可 | **采用** |
| B. 自定义 RTP/UDP | 可 <50ms | 低 | 需自写 jitter buffer/解码/AudioWorklet，工作量反而更大 | 手工打洞，麻烦 | 备选，不推荐 |
| C. WebSocket 传 PCM/Opus | 100-400ms 且抖动大 | 最低 | AudioContext 缓冲手调 | 不可用 | 仅作开发期调试手段 |
| D. SRT/RTSP + WebCodecs | 中 | 高 | 新 API，兼容性一般 | — | 过度设计 |

### 3.2 推荐 WebRTC 的理由

1. 对讲机窄带语音（~3kHz 音频带宽）用 Opus 16kHz/24kbps 足够，"质量可妥协"完全满足。
2. 浏览器端播放/抖动/回声消除全部原生解决，客户端零插件；麦克风采集自带 AEC/AGC。
3. 局域网与 WireGuard 隧道内 P2P 直连，**不需要 STUN/TURN**；后期公网只需部署一个 coturn，架构不变。
4. 时延预算（LAN）：采集 10-20ms + Opus 20ms 帧 + 网络 <5ms + jitter buffer 40-80ms + 播放 ≈ **80-150ms**，PTT 指令走 WS <50ms。对半双工业余通联完全够用；可通过 Chrome `playoutDelayHint` 进一步压低。
5. 带宽：语音 ~30kbps + 屏幕 <100kbps，WireGuard 隧道无压力。

### 3.3 降级与备选

- **CPU 兜底**：WebRTC 里浏览器原生支持 PCMU(G.711)，Pi 端几乎零编解码开销；aiortc 内置支持，切换只改编码器参数。
- **整机兜底**：若树莓派上 aiortc 仍吃紧，可整体换 **Go + Pion + PCMU**（单二进制、~20MB 内存），协议层代码全部可平移。默认不启用。

### 3.4 HTTPS 约束（重要）

浏览器麦克风（getUserMedia）要求安全上下文：`https://` 或 `localhost`。局域网用 **自签证书**（`tools/make_cert.sh` 生成，首次访问接受一次警告），这也是后期公网部署的自然路径（届时换 Let's Encrypt）。开发期可用 Chrome flag `unsafely-treat-insecure-origin-as-secure` 应急。

## 4. 硬件方案

### 4.1 树莓派

**树莓派 4B**（已确认）——性能富余，aiortc 无压力，PCMU/Go 兜底仅在实测异常时启用。

### 4.2 音频通路（定稿：AIOC 音频口直连）

早期"音频与 UART 混线"的判断有误（已撤销）：查 AIOC 原理图，音频与数据/PTT 分处不同触点（见 §1.2 表）——**SPK+（对讲机→主机收音）独占 2.5mm Tip，MIC+（主机→对讲机发话）独占 3.5mm Ring**，均无数据混入。因此：

- **收音**：AIOC 声卡采集（48kHz 单声道）直接取 SPK+，无噪声、无需低通/内部改装/声学耦合。
- **发话**：AIOC 播放走 MIC+ 独立触点，与 PTT1（Sleeve）、屏幕流（2.5mm Ring）互不干扰；发射期间音频照常播放。
- **PTT 稳定**：唯一约束仍是 §1.2 的结论——DTR 电平 PTT 吸合期间静默串口数据（TXFRCPTT 数据优先仲裁）。
- 曾规划的"声学耦合（A1）/内部抽头（A2）/AIOC 待测（A3）"三级路线作废：AIOC 即直连方案，实测屏幕流正常时音频链路同链路验证（M2 `audio_loopback.py`）。
- EMI 注意保留：大功率发射时 RF 可能窜入 USB 线，建议磁环/地网、适当降功率。

### 4.3 其他

- 高点部署注意：防雨外壳、天线引出、Wi-Fi 覆盖（或后续 WireGuard over 现有路由）、供电（UPS hats 或大容量充电宝）。
- EMI：大功率发射时 RF 可能窜入 USB 线导致设备掉线，建议磁环/地网（tiger tail）、适当降功率。
- BOM：树莓派 4B ×1、编程线 ×1、USB 声卡 ×1（A1/A2）、自制药耦线材（A2）、电源与外壳若干。

## 7. 安全与业余无线电合规

- **防误发射**：UI 发射需"上电（ARM）"开关 + 按住说话；服务端最长发射时限（默认 180s，可配）；WS 断连即撤 PTT；对讲机 TxTOut 兜底。
- **鉴权**：HTTPS + 首次登录设置的操作员 token；后续多用户再扩展权限。
- **单操作员锁**：同一时刻仅一个会话可发控制指令/PTT，避免抢机。
- **合规提醒**：发射功能仅供持照业余电台使用，界面提供呼号标识提醒、发射计时显示；建议在信道配置上限制合法频段与功率档位。
- 数据不出局域网/VPN（公网阶段除外），无第三方云依赖。

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| v1 推流为阻塞发送，38400 下整帧 ~240ms | 只影响推流瞬间主循环变慢（与 V3 相同设计），按键注入在帧间隙仍被及时解析；实测评估是否需要固件侧分片发送 |
| PTT 吸合期间发数据导致 PTT 被强制释放 | **发射期静默保活/注入**（已实现于探测工具与服务端设计）；静默不影响 DTR 控制传输，看门狗随时可撤 |
| PTT 期间屏幕流中断 | 预期行为（保活停止 + RXIGNPTT 丢收流），松键自动补整帧；发射中无需看屏 |
| 进程崩溃/断线时 PTT 卡死 | AIOC 电平随端口关闭正确释放、对讲机停发（已实测）；**但对讲机固件在发射中途失去宿主后出现过推流停滞（半帧后静默、保活无响应），断电重启 + 一次正常会话后恢复**——部署文档要求：配置 TxTOut 兜底 + 异常后重启对讲机并跑一次正常收流会话；服务端打开串口时无条件清 DTR/RTS（防 pyserial 默认拉起误触发，已实测对收流无影响） |
| 屏幕流"消失"（对讲机闲置后） | **SetOff 自动深睡**：固件深睡倒计时只认射频收发，串口保活不阻止入睡（源码 app.c:1683），睡后推流静默、保活唤不醒；对策：**部署电台菜单 SetOff=OFF（必配）**+ 服务端停滞检测（>6s 无帧自动注入 EXIT 唤醒，已实现）；省电模式空闲时 ~0.5s 一帧的慢流属正常，非故障 |
| 语音端到端延迟 | **已修复（实测 ~2s → 预期 150-350ms）**：① 采集队列在 WebRTC 握手期间积压成固定 ~1s 陈旧延迟 → 首次 recv 惰性启动采集 + 每帧裁积压到 3 帧（丢帧同步推进 pts 保持时轴对齐）+ 队列硬上限 8 帧；② sounddevice 显式 `latency="low"`（Windows 默认延迟高）；③ 浏览器 NetEQ 自适应膨胀 → `jitterBufferTarget=60ms`；④ 发话缓冲硬上限 500ms。延迟预算：收听 ~150-250ms、发话 ~250-350ms |
| 屏幕流红灯位与实际 TX 短暂失步 | PTT1 吸合期间收流被 AIOC `RXIGNPTT` 丢弃，红灯位在 PTT1 路径发射期间**不可读**（TX 确认靠对讲机自身指示灯/空中信号；红灯位仅在键上前后可用） |
| 保活节奏/推流行为与推断不符 | 已用 `serial_probe.py` 实测（38400、整帧+差分、~3-4fps 静态刷新均符合预期）；节奏可配置 |
| 声卡电平不匹配/地环噪声 | AIOC 音频电平可经 aioc-util 调节（固件 ≥1.4）+ 软件增益；audio_loopback 电平表实测 |
| Pi 上 aiortc 偏重（4B 概率低） | 切 PCMU；仍不足则换 Go+Pion（协议代码平移） |
| 浏览器自动播放策略 | "开始收听"按钮点击后再建播放（已实现），标准做法 |
| 固件升级协议变化 | 协议文档 + 解析层单测；v1/v3 差异集中在变体配置里 |

## 9. 已确认项

1. 对讲机硬件：**UV-K5 V1**（DP32G030），K 型两芯口。
2. 目标固件：**`uv-k5-firmware-custom-remote`**（用户自研，V1 基础 + 串口控制）；`uv-k1-k5v3-firmware-custom`（V3/K1）保留为兼容目标，服务端以 `variant` 配置切换。
3. 树莓派 4B。
4. PTT：**定稿 = DTR 电平 + 发射期静默保活**（零固件改动，实测可用）；CM108 GPIO4→PTT2 因引脚与机型键控位置对不上弃用；串口帧 PTT 固件补丁存档作备份。AIOC 承担**控制串口 + 音频 + PTT** 三个角色（单线方案）。
5. 音频通路：AIOC 音频口直连（SPK+ 收音 / MIC+ 发话，独立触点无混线），M2 用 `audio_loopback.py` 验证。
6. 手机浏览器适配在 M5 顺带支持。
